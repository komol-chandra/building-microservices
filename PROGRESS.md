## Decision log
- 2026-11-10 — 3 services: Product, Inventory, Order. Custom Express gateway. JWT checked in the gateway. One Postgres container with 3 DBs. Work phase by phase, Claude explains each step.

- 2026-11-10 — Phase 0: each service gets its own Postgres **user** too (not only its own DB), and REVOKE CONNECT FROM PUBLIC, so isolation is enforced by the DB rather than by convention. Svc users have CREATEDB for Prisma's shadow DB. Host has Node 18 / no yarn → everything runs on node:20 in Docker.
- 2026-11-10 — Phase 1: Prisma **6** (not 7, which needs driver adapters + prisma.config.ts), Express **5** (async errors reach the handler automatically), Zod **4**. Stock changes use a conditional `updateMany WHERE available >= qty` (atomic) instead of read-check-write. RESERVE/RELEASE are rejected by the admin API, only the saga may use them. Compose `init: true` + `exec` in CMD for graceful SIGTERM. Migrations are created with `docker compose run --rm <svc> yarn prisma migrate dev --name X`, then chown the files (container runs as root).
- 2026-11-10 — Phase 2: F1 uses a **compensating delete** (no distributed transaction). Product list has no stock (avoids N+1 HTTP calls); detail page has it. product-service does NOT `depends_on` inventory. Price is Decimal(10,2), validated as a string with max 2 decimals; Prisma prints it without trailing zeros ("18"), so the UI formats it. **Gotcha found:** Zod 4 `.partial()` keeps `.default()`s → update schema must be built from a base without defaults.
- 2026-11-10 — Phase 3: route table = list of {method, path, service, roles} (more precise than prefix-only). Gateway strips client `x-user-*` headers globally, then sets them from the verified JWT. `express.json()` only on /auth/login so proxied bodies stream untouched. JWT HS256 pinned. Demo users `admin@shop.test/admin123`, `user@shop.test/user123`. `POST /inventories` is deliberately NOT routed (internal, product-service only). Login limit 10/min, global 300/min. Services no longer publish host ports; Authorization header is still forwarded to services (harmless, could be stripped later).
- 2026-11-10 — Phase 4: client sends only `{productId, quantity}`, never a price; prices come from product-service. Duplicate productIds are merged. Only PUBLISHED products can be ordered. Totals use Prisma.Decimal, half-up to 2 dp; `TAX_RATE` env (default 0.05), discount fixed at 0 for now. Order + LineItems saved in one nested create (same DB → real transaction). Stock is NOT checked here (Phase 5 saga does it). Orders are scoped to `x-user-id` for every role (admin sees only own orders too); another user's order → 404 not 403. order-service rejects requests without `x-user-id` (401). Does not `depends_on` product-service.
- 2026-11-10 — Phase 5: same `events/rabbit.ts` copied into inventory and order (no shared package). Both services declare the WHOLE topology on connect, so an event published before its consumer ever started is not dropped. Publisher confirms + persistent messages; ack only after the handler's DB commit; invalid (Zod) messages are nacked without requeue, handler errors requeue after 3s (DLQ is Phase 8). Rabbit connect is retried in the background, HTTP serves meanwhile; `/health` shows `rabbit: up|down`. **Inventory also has a ProcessedEvent table** (not only order) and stores the result event it sent, so a duplicate `order.placed` re-sends the same answer instead of reserving twice. All items of an order are reserved in one transaction, locked in productId order (no deadlocks); any shortage rolls back the whole order. Order only moves out of PENDING (late/duplicate events can't flip a final status). If publishing `order.placed` fails the order is marked FAILED and POST returns 503 (compensation); known gap: if the broker actually got the message, stock stays reserved for a FAILED order → outbox in Phase 8. Reserved stock currently stays in `reservedQuantity` (no shipping/release step yet). Gotcha: RabbitMQ management stats lag ~5s. Host DNS gotcha: `yarn add` inside a compose container failed (EAI_AGAIN); ran it with `docker run --network host node:20-slim` instead.
- 2026-11-11 — Phase 6: Vite 6 + React 18 + react-router 6 + axios, plain CSS (no UI kit). Browser calls the gateway at `http://localhost:8081` (host port, `VITE_API_URL`), not the Docker DNS name. JWT + user in localStorage (`ms.session`); 401 on any call → clear session, go to /login. Role checks in the UI only hide pages; the gateway enforces them. Cart is client-only (localStorage), checkout sends only `{productId, quantity}`. Order detail polls `GET /orders/:id` every 1s while PENDING (list every 2s while any PENDING); stops at a final status. Shoppers see `status=PUBLISHED` only, admin sees all. Quantity is NOT capped at shown stock so the saga's FAILED path is easy to try. Vite uses polling file watch (bind mount). Deps installed with `docker run --network host` (same DNS gotcha as Phase 5).

- 2026-11-11 — Phase 7: one Dockerfile per app with stages `base → deps → dev | build → prod`; compose picks `target`. Prod = compiled JS + `yarn install --production` + `USER node`. **`prisma` moved to dependencies** because the prod container runs `prisma migrate deploy` on start (yarn.lock unchanged: it doesn't record dev vs prod). Prod stack = `docker-compose.prod.yaml` layered on the dev file, `volumes: !reset []` removes bind mounts (needs Compose ≥ 2.24). Client prod = `vite build` → nginx with SPA fallback; `VITE_API_URL` is a **build arg** (Vite inlines it). Healthchecks use `node -e fetch(...)` (no curl in slim images). Gateway healthcheck = gateway process only (/health answers 200 or 207). Services still do NOT `depends_on` each other; only the seed job waits for `service_healthy` (gateway, product, inventory). Seed goes through the gateway API, not SQL (creating a product spans two DBs; product-service owns that logic), and skips existing SKUs. Gotchas: Alpine resolves `localhost` to `::1` and nginx listened on IPv4 only → healthcheck failed until `listen [::]:80`; zsh doesn't word-split `$VAR` in commands (use `COMPOSE_FILE=a:b`).
- 2026-11-11 — Phase 8: **Retry/DLQ**: per consumed queue Q, `Q.retry` (x-message-ttl 5s, dead-letters back to Q via the default exchange) and `Q.dlq`. Main queues keep NO arguments (re-declaring an existing queue with new args fails). Consumer moves the message (publish to target with confirm, THEN ack) with headers `x-attempt`, `x-last-error`, `x-original-routing-key` (needed: after a retry the routing key is the queue name). Invalid → DLQ at once; handler error → retry, 5th failure → DLQ (`RABBITMQ_MAX_ATTEMPTS`). Shovel plugin enabled so the UI can "Move messages" from a DLQ. **Outbox** in order-service only: `OutboxEvent` row in the same transaction as the order; relay polls every 1s (`OUTBOX_POLL_MS`) + a kick after each order; `FOR UPDATE SKIP LOCKED`, oldest first, stops at the first failure; published rows deleted after 7 days. POST /orders no longer returns 503 when RabbitMQ is down (order stays PENDING until the broker is back). Inventory doesn't need an outbox: it stores its answer in ProcessedEvent before publishing, and an unacked order.placed is redelivered and re-sends it. **Correlation id**: `context.ts` per service (AsyncLocalStorage + `log.*` + `requestIdMiddleware`), axios interceptors forward `x-request-id`, AMQP `correlationId` property on publish, consumers restore it; the outbox stores it per row. **Tests**: Vitest in `test/` (outside `src`, so tsc/prod builds ignore them); pricing extracted to `pricing.ts` to be testable; e2e is its own package under `tests/e2e`, run as compose service `e2e` (profile `test`) inside the network. Fixed on the way: order-service logged "→ FAILED" even when it ignored a non-PENDING order. Note: each e2e run leaves one garbage message in `inventory.order-placed.dlq` (that's the DLQ test).
- 2026-11-11 — Phase 9: auth-service (scrypt via node:crypto, no native deps) signs **RS256**; private keys in a `SigningKey` table (study shortcut, KMS in real life), created on first start; `kid` in every token; `yarn rotate-key` adds a key (old one stays in JWKS). Gateway: `jsonwebtoken` → `jose`, `createRemoteJWKSet` with `cacheMaxAge: Infinity` (works while auth is down) and **`cooldownDuration: 5000`** — found in testing that jose's default 30s cooldown made tokens from a freshly rotated key 401 for up to 30s. JWKS fetch failure → 503 (not 401), client only logs out on 401. Issuer + audience checked. `/auth/*`, `/users*`, `/.well-known/jwks.json` are plain config.json routes; login/register rate limit stays in the gateway. Demo users seeded in the migration with the **same UUIDs** (old orders keep their owner). Register never takes a role; email trimmed+lower-cased (**gotcha:** Zod 4 `z.email().trim()` validates before trimming → use `z.string().trim().toLowerCase().pipe(z.email())`). **`x-user-name` is URL-encoded** by the gateway (header values must be ASCII; registered names may not be), order-service decodes it. `/auth/me` reads the DB, not the token. Admin can't change own role. auth_db created by idempotent `infra/postgres/02-auth.sql` (mounted for new volumes, run by hand for the existing one).
